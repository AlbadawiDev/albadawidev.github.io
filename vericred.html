Certificate verification · Django · Case study 03

VeriCred

Issue certificates through an approval workflow, then verify their status through a public QR link.

Python / Django / QR codes / SQL

Inspect source & reviewed changes ↗

The problem

A certificate is useful only when its status can be checked and its issuance can be attributed. VeriCred separates drafting, approval and issuance, while keeping unpublished certificates private.

The implemented workflow

  1. An authorized issuer creates and submits a draft.
  2. A reviewer approves or rejects it; the decision records the reviewer.
  3. An issuer completes issuance and generates an absolute QR verification URL.
  4. Anyone can verify an issued certificate; drafts and pending records remain unavailable.
  5. Authorized staff inspect the audit trail or revoke a certificate.

Architecture and decisions

Django models represent profiles, certificates and audit events. Role and ownership checks guard transitions and editing. Transactions keep workflow changes consistent with their audit entries. The public verification endpoint exposes issued/revoked statuses only; deployment configuration validates its public origin and security settings.

Current boundaries

The reviewed changes are on the linked pull request. PostgreSQL locking and production concurrency were not tested; SQLite does not implement row locks. The application needs operational authentication/rate limits before an Internet deployment. Screenshots contain fictional data.
